# 7.14.14 — безопасная подготовка реляционного переноса

## Реализовано

- Проверка реальных словарей-контейнеров V7: vehicles используют vehicle_id,
  requests — id; ключ passes является номером, а не ID пропуска.
- Конфликты ключа/ID не исправляются молча; события проверяются по постоянному ID.
- administrative_passes/unknown — отдельные негостевые контексты; исторический
  current требует разбора и никогда автоматически не связывается с сегодняшним заездом.
- Несколько старых карточек с одним номером отмечаются для разбора идентичности,
  не объединяются и не удаляются.
- SQLite Store: отмена coroutine больше не отпускает блокировку до завершения
  транзакции executor. После успешного commit обновляется локальная ревизия,
  затем передаётся отмена; при ошибке локальная ревизия не увеличивается.

## Границы установки

Обновление Gateway устанавливает исправленную диагностику. Восемь уже скопированных
в HA SQL-адаптеров автоматически не заменяются. Исправление отмены записи должно
устанавливаться отдельной проверенной операцией: проверка исходных SHA всех восьми
файлов, свежий backup, точная замена, config check, один restart и контроль записей.
Не повторять первичную миграцию и не заменять живую базу файлом.

Нормализованные таблицы не заполняются и источник бизнес-истины не переключается.

## Требования следующего этапа

Автомобиль — постоянная сущность, участие в заезде — отдельная связь. Все старые
vehicle_id сохраняются в таблице сопоставления с источником; слияние только после
проверки идентичности. Номер не является достаточным доказательством слияния.

Пропуск и заявка — самостоятельные записи со стабильными ID и историей статусов.
Для административного пропуска stay_id допустимо NULL при явном назначении;
гостевой пропуск обязан ссылаться на заезд. Нельзя создавать фиктивную гостевую
заявку для старого административного пропуска: нужна явно описанная legacy-провенанс.
Текущие ограничения schema 11 требуют версионированного изменения до импорта.

Исторические въезды/выезды не перезаписываются при переклассификации автомобиля.
Исходное событие сохраняется; исправление классификации — отдельная запись аудита.
Неизвестная связь отмечается как нерешённая, а не угадывается по имени или датам.

Условия переключения: полные исходные снимки и SHA; сопоставление каждой записи;
сверка связей и финансов без перерасчёта; повторяемый импорт без дублей; транзакции
с CAS и request_id; тесты сбоев и restart; сравнение старого/нового чтения; отдельный
план восстановления после появления новых записей. Старый backup нельзя просто
накладывать на базу после начала новых записей без их сверки и сохранения.
